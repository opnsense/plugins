# GitHub Release Package Repository Design

## Goal

Publish signed `os-bind-rp` package repositories from GitHub Releases, without
committing package binaries to a source branch.

## Distribution model

The fork moves to `resolver-plugins/plugins`. Public GitHub Releases transport
the package repositories. GitHub Pages remains binary-free at
`https://resolver-plugins.github.io/plugins/`, serving bootstrap configuration,
the public key, and documentation.

Each supported OPNsense major/minor series owns one persistent Release channel:
`pkg-26.1`, `pkg-26.7`, and future `pkg-<major>.<minor>` channels. A channel
contains a flat, signed FreeBSD `pkg` repository: the current production
package and the catalog files generated by `pkg repo`. The generated repository
configuration points directly to that Release asset root.

Initial channels retain only their current package. Git source history, merged
pull requests, Release notes, and `build-metadata.txt` provide the audit trail.

## Source and versions

`master` owns CI and publication. `release/bind-rp/<series>` owns reviewed BIND
source and immutable upstream provenance for one series.

`PLUGIN_VERSION` follows upstream plugin versions. `PLUGIN_REVISION` is a
monotonic Resolver Plugins change counter; an out-of-band fix advances
`os-bind-rp-1.36_3` to `os-bind-rp-1.36_4`. Neither encodes an OPNsense point
release. `PLUGIN_MANIFEST_DEPENDS` controls compatibility, currently requiring
`opnsense >= 26.1.11_10`.

An unchanged OPNsense fix release receives a compatibility build, not a
same-version public republish. If it requires a package change, a small
release-branch PR updates metadata and increments `PLUGIN_REVISION`.

## Workflows

A manually dispatched development workflow validates a pull request targeting a
release branch, builds it in its declared FreeBSD VM, and replaces a
`pr-<number>-<series>` GitHub pre-release. The pre-release contains a
development package and build metadata, is deleted when the PR closes or
merges, and never receives the repository signing secret.

A master-controlled production workflow runs only after a PR merges into
`release/bind-rp/<series>`. It uses the trusted merged source, builds it,
validates package and provenance, creates a fresh signed catalog, and updates
`pkg-<series>`. Upload the package first and catalog assets last. Protected
release branches make the reviewed merge the publication authorization.

The existing daily synchronizer discovers upstream `stable/<series>` branches
and the matching FreeBSD base dynamically from `opnsense/tools`. It must derive
new channel names from the discovered series. An unchanged-BIND new series
bootstraps and publishes automatically; an upstream BIND change remains a
ready-to-merge review PR whose merge publishes the channel.

## Security and verification

The private signing key is an Actions secret available only to production jobs.
Repository generation, package/version validation, and signing complete before
any Release asset is changed. A failed publication reruns safely: clients keep
the old catalog until the new one is uploaded.

One manual proof uses a disposable GitHub test pre-release, an ephemeral key,
and the FreeBSD development VM to prove `pkg update` and installation through
the actual Release URL. Routine production publication does not deploy to any
firewall or add a post-publication test stage.
